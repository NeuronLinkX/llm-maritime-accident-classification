# `flat/labels.csv` 컬럼 가이드

`outputs/step4_persona_ablation/flat/labels.csv`(및 `labels.parquet`)의 모든 컬럼을 설명합니다. 이 표는 **군집(cluster) × 체인 단계(persona_01/02/03) × 조건(identity_on/off)** 조합마다 한 행씩 있습니다.

- 군집 5개 기준 30행

## 어떤 컬럼부터 봐야 하나

- **최종 KMST 레이블만 보고 싶다면**: `stage` 컬럼에서 `persona_03`인 행만 필터링 → `root_cause_primary` 컬럼을 보세요.
- **정체성 유무 효과를 비교하고 싶다면**: 같은 `doc_id`(군집)를 `condition`이 `identity_on`/`identity_off`인 두 행으로 나란히 놓고 비교하세요.

---

## 1. 모든 단계 공통 컬럼

| 컬럼                     | 타입                 | 의미                                                                                                                                                                                                 |
| ------------------------ | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `doc_id`               | 문자열               | 군집 식별자 (`cluster_0` ~ `cluster_4`). 이름은 "문서 id"지만 실제로는 군집 id다 — 개별 재결서 단위가 아니라 군집 단위이기 때문.                                                                |
| `n_docs`               | 정수                 | 이 군집에 실제로 속한 원본 재결서 건수 (예:`cluster_3` = 263건). 군집이 얼마나 큰지 참고용.                                                                                                        |
| `stage`                | 문자열               | 체인 단계 —`persona_01`(사실·패턴 구조화) / `persona_02`(원인 후보 검증) / `persona_03`(레이블 확정).                                                                                        |
| `condition`            | 문자열               | `identity_on`(정체성 문구 포함) / `identity_off`(정체성 문구 제거, 나머지는 완전히 동일).                                                                                                        |
| `schema_valid`         | 불리언               | 모델 출력이 JSON으로 파싱되고 요구 스키마(필수 필드·enum 등)를 만족했는지.`False`면 그 행의 레이블·수치 컬럼은 전부 비어있다.                                                                    |
| `parse_retry`          | 정수(0/1)            | 파싱 실패 시 재시도했는지 여부. 기본 설정은 재시도 없음(0) — greedy 디코딩에서는 같은 프롬프트를 다시 넣어도 같은 결과가 나오므로, 재시도하려면 프롬프트 자체를 바꿔야 하고 그 경우만 1로 표시된다. |
| `think_block_stripped` | 불리언               | 모델이`<think>...</think>` 형태의 내부 추론 블록을 출력해서 제거했는지. Qwen3는 기본적으로 이걸 낼 수 있어 발생률 자체를 지표로 남긴다.                                                            |
| `prompt_tokens`        | 정수                 | 이 호출에 실제로 들어간 입력 토큰 수.                                                                                                                                                                |
| `completion_tokens`    | 정수                 | 모델이 실제로 생성한 출력 토큰 수.`max_new_tokens`(현재 4096)와 정확히 같으면 잘렸다는 뜻이니 의심해볼 것.                                                                                         |
| `latency_sec`          | 실수                 | 이 호출 1건의 생성 소요 시간(초).                                                                                                                                                                    |
| `timestamp`            | 문자열(ISO8601, UTC) | 이 결과가 저장된 시각.                                                                                                                                                                               |
| `raw_text`             | 문자열               | 모델이 실제로 뱉은 원문 그대로(수정 없음). 디버깅용 — 셀이 매우 길다.                                                                                                                               |
| `parse_error`          | 문자열 또는 빈값     | 파싱 실패 사유 (예:`JSON_DECODE_FAILED`). 성공했으면 비어있음.                                                                                                                                     |
| `extra`                | 문자열(JSON)         | 스키마 검증 세부 오류 목록. 성공했으면 빈 배열`[]`.                                                                                                                                                |

## 2. `persona_01`(사실·패턴 구조화) 전용 컬럼

다른 단계 행에서는 전부 빈값(null)입니다.

| 컬럼                      | 의미                                                                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| `n_facts`               | 추출한 "사실" 항목 개수                                                                             |
| `n_evidence`            | 추출한 "증거" 항목 개수                                                                             |
| `n_actors`              | 추출한 행위자(역할) 개수                                                                            |
| `n_vessels`             | 추출한 선박 개수                                                                                    |
| `n_missing_information` | "확인 안 됨"으로 표시한 누락 정보 개수                                                              |
| `handoff_status`        | 다음 단계로 넘겨도 되는지 자체 판단 (`READY_FOR_PERSONA_2` 정상 / `RETURN_FOR_CORRECTION` 반려) |

> 참고: 이건 실제 **레이블링이 아니라 "얼마나 뽑아냈는지" 개수 요약**입니다. 각 사실/증거 항목이 실제로 어떤 카테고리(사실상태·증거유형)로 분류됐는지는 이 표에 없고, `parsed/{doc_id}/persona_01/{condition}.json` 원본 파일 안에만 있습니다.

## 3. `persona_02`(원인 후보 검증) 전용 컬럼

| 컬럼                     | 의미                                                          |
| ------------------------ | ------------------------------------------------------------- |
| `n_cause_candidates`   | 검증한 원인 후보 개수                                         |
| `n_alternative_causes` | 대체 원인으로 분류한 개수                                     |
| `n_legal_conflicts`    | 법령 충돌로 표시한 개수                                       |
| `n_unresolved_issues`  | 미해결 쟁점으로 표시한 개수                                   |
| `handoff_status`       | `READY_FOR_PERSONA_3` 정상 / `RETURN_FOR_CORRECTION` 반려 |

마찬가지로 이건 개수 요약이고, 각 원인후보의 세부 분류(인과단계·원인범주)는 `parsed/{doc_id}/persona_02/{condition}.json` 안에만 있습니다.

## 4. `persona_03`(레이블 확정) 전용 컬럼 — 최종 산출물

| 컬럼                      | 타입                   | 의미                                                                                                                                                                                                    |
| ------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accident_type`         | 문자열                 | 이 군집의 대표 사고 유형 (모델이 채우지 않으면 비어있을 수 있음. 알려진 한계).                                                                                                                         |
| `root_cause_primary`    | 문자열                 | **최종 주원인** : KMST 공식 분류체계(운항과실/취급 불량 및 결함/기타 세부항목) 중 기여도 점수가 가장 높은 것 하나.                                                                               |
| `root_cause_secondary`  | 문자열(JSON 리스트)    | 주원인 외 나머지 원인 후보 목록, 기여도 점수 내림차순.                                                                                                                                                  |
| `n_causes`              | 정수                   | 이 군집에 대해 모델이 매긴 원인 개수(주원인+부원인 합계).                                                                                                                                               |
| `analytic_contribution` | 문자열(JSON)           | `[{"label_code": ..., "score": ...}, ...]` 형태 — 원인별 분석용 기여도 점수(0~1, 법적 효력 없는 연구지표).                                                                                           |
| `official_ratio`        | 문자열(JSON) 또는 빈값 | 재결서에**명시적으로** 적힌 공식 원인제공비율이 있으면 그 원문, 없으면 `present: false`. 모델이 추정해서 채우면 안 되는 필드.                                                                   |
| `taxonomy_valid`        | 불리언 또는 빈값       | `root_cause_primary`/`root_cause_secondary`에 쓰인 값들이 전부 `kmst_official_taxonomy.json`의 실제 22개 세부항목 안에 있는지. `False`면 모델이 목록에 없는 값을 지어냈다는 뜻(품질 경고 신호). |

## 자주 헷갈리는 점

1. **`doc_id`인데 왜 군집 이름이 들어있나** — 애초에 문서(재결서) 단위로 설계했다가, 군집 단위 분석으로 바뀌면서 컬럼 이름은 그대로 두고 값만 군집 id로 채웠기 때문입니다. 컬럼명 자체가 오해 소지가 있다는 점 참고하세요.
2. **`persona_01`/`persona_02` 행에는 왜 `root_cause_primary`가 비어있나** — 최종 KMST 레이블은 오직 `persona_03` 단계에서만 나오도록 설계돼 있습니다(체인 구조상 P01은 사실만, P02는 인과구조만 다룸). P01·P02의 분류 필드(사실상태·증거유형·원인범주 등)는 이 표에 없고, 각 단계의 원본 JSON 파일에만 있습니다.
3. **같은 군집인데 `identity_on`/`identity_off` 결과가 다를 수 있다** — 이게 바로 이 실험이 측정하려는 것입니다. `root_cause_primary`가 다르면 "정체성 부여가 레이블에 실제 영향을 줬다"는 뜻이고, 같으면 "영향이 없었다"는 뜻입니다.
4. **`raw_text`, `extra`는 평소엔 안 봐도 됩니다** — 디버깅/재현성 검증용입니다.
